1. SUMMARY & TYPE:
   [Bug Fix | RFC 3264 WebRTC SDP Compliance] Conform SDP Answer Direction for Inactive m-sections (`a=inactive`)

2. REASON & TECHNICAL EVIDENCE:
   - When a client participant unpublishes a media track (such as stopping screen share or muting a track with transceiver inactivation), the browser WebRTC transceiver is transitioned to `inactive`.
   - The browser generates an offer containing an inactive m-section per RFC 3264 Section 6.1:
     `m=video ...`
     `a=mid:3`
     `a=inactive`
   - Currently, `signaling-coordinator`'s SDP translation layer (which converts between browser SDP offers/answers and mediasoup ORTC objects) echoes `a=recvonly` (or `a=sendrecv`) in the SDP answer for that inactive m-section instead of `a=inactive`.
   - Per RFC 3264 Section 6.1: "If a stream is offered as inactive, the answer MUST be inactive."
   - In standard Chromium and WebKit WebRTC engines (`sdp_offer_answer.cc`), receiving `a=recvonly` in response to an `a=inactive` offer throws:
     `Failed to execute 'setRemoteDescription' on 'RTCPeerConnection': Failed to set remote answer sdp: Incompatible send direction`
   - This failure causes publisher renegotiation to abort (`unable to set answer`), triggers negotiation timeout after 15 seconds, and causes WebSocket signaling disconnection.
   - Note: While `web-client-pwa` has implemented client-side fallback sanitization (`conformAnswerSdp`), RFC 3264 compliance requires the server-side SDP answer generation in `signaling-coordinator` to conform natively.
   - (Architectural context: Originally submitted by web-client-pwa to sfu-media-node as REQ-002, but triaged and redirected here because sfu-media-node is a pure ORTC media plane without SDP handling).

3. EXPECTED BOUNDARY BEHAVIOR:
   - In `signaling-coordinator`'s SDP synthesis/answering logic:
     When constructing an SDP answer to send to the browser over the signaling WebSocket:
     If the incoming offer m-section has direction `a=inactive`, the corresponding m-section in the generated SDP answer MUST also have `a=inactive`.

4. RESOLUTION & ARCHITECTURAL TRIAGE:
   - Decision: ACCEPTED & IMPLEMENTED
   - Architectural Justification:
     1. Strictly preserved Hexagonal Architecture boundaries and SRP/DIP: all SDP parsing and synthesis remains completely isolated in `internal/adapters/inbound/livekit/sdp_mapper.go` without leaking SDP concepts or Pion data structures into `internal/domain` or `internal/ports`.
     2. Implemented RFC 3264 Section 6.1 conforming direction mapping:
        - `getOfferDirection` extracts transmission direction from media level (or inherits from session level), treating port 0 as inactive.
        - `determinePublisherAnswerDirection` maps inactive / port 0 / recvonly offers to `a=inactive`, and sendonly / sendrecv offers to `a=recvonly`.
        - `GeneratePublisherAnswer` sets `a=inactive` instead of `a=recvonly` for inactive or rejected m-sections, and preserves port 0 if offered with port 0.
        - RFC 8843 Section 7.3: Excludes rejected (port 0) m-sections from the answer's `a=group:BUNDLE` attribute.
     3. In `ParsePublisherOffer`, skipped inactive or recvonly media sections from being parsed into active publisher tracks, preventing unwanted `Produce` calls or track registration for inactive transceivers.
   - Modified Files:
     - `internal/adapters/inbound/livekit/sdp_mapper.go`: Added `getOfferDirection`, `determinePublisherAnswerDirection`, updated `GeneratePublisherAnswer` and `ParsePublisherOffer`.
   - Added Tests:
     - `TestSDPMapper_GeneratePublisherAnswer_InactiveMSection_ConformsRFC3264_REQ001` in `internal/adapters/inbound/livekit/sdp_mapper_test.go`
     - `TestSDPMapper_GeneratePublisherAnswer_AllInactive_REQ001` in `internal/adapters/inbound/livekit/sdp_mapper_test.go`
     - `TestSDPMapper_GeneratePublisherAnswer_PortZeroRejectedMSection_REQ001` in `internal/adapters/inbound/livekit/sdp_mapper_test.go`
     - `TestLiveKitWSHandler_OfferAnswer_InactiveMSectionConformsRFC3264_REQ001` in `internal/adapters/inbound/livekit/ws_handler_test.go`
   - Verification: All tests pass cleanly under `go test -v -race -count=1 ./...` with zero race conditions.

1. SUMMARY & TYPE:
   [Bug Fix | Video Quality & Framerate Degradation] Decouple Temporal Layer from Spatial Layer in SignalRequest_TrackSetting and Support TrackSetting.disabled

2. REASON & TECHNICAL EVIDENCE:
   - In `internal/adapters/inbound/livekit/ws_handler.go` lines 450-453:
     ```go
     spatial := int32(trackSettings.GetQuality())
     temporal := spatial
     for _, sid := range trackSettings.GetTrackSids() {
         if err := h.coordinator.SetConsumerLayers(ctx, roomID, identity, sid, spatial, temporal); err != nil {
     ```
   - When a browser client requests lower video quality (e.g. `web-client-pwa` AdaptiveViewportManager selecting LOW quality for thumbnail / grid tiles):
     - `trackSettings.GetQuality()` is `VideoQuality_LOW` (`0`).
     - `temporal` is forcefully set to `0`.
   - In `sfu-media-node` (Mediasoup SFU), setting `temporal_layer: 0` instructs the SFU to throttle the consumer down to the lowest temporal framerate (7.5 fps).
   - This causes video playback to become extremely slow, choppy, and laggy ("خیلی کند میشه") even when bandwidth is healthy.
   - For multi-user video grids, clients want lower spatial resolution (e.g. 180p or 360p) while preserving smooth framerate (30 fps or highest available temporal layer).
   - Furthermore, when `trackSettings.GetDisabled()` is true (e.g. offscreen video tile), `ws_handler.go` currently ignores the `disabled` flag and does not call `SetMediaPaused(true)`.

3. EXPECTED BOUNDARY BEHAVIOR:
   - In `internal/adapters/inbound/livekit/ws_handler.go`:
     1. When `trackSettings.GetDisabled()` is true, pause the consumer via `SetMediaPaused(..., true)`. When false, resume via `SetMediaPaused(..., false)`.
     2. In `SetConsumerLayers`, decouple temporal layer from spatial layer:
        Set `temporal := -1` (or highest layer / omit temporal constraint) so the SFU does not throttle the framerate down to 7.5 fps when spatial resolution is downgraded.
