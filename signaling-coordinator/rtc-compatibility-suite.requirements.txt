RFC / REQUIREMENT ID: REQ-001
SOURCE SERVICE: rtc-compatibility-suite
TARGET SERVICE: signaling-coordinator
STATUS: IMPLEMENTED
===================================================================

1. SUMMARY & TYPE:
   [Bug Fix | Contract Compliance] SignalResponse_Answer must include Answer.Id matching SignalRequest_Offer.Id

2. REASON & TECHNICAL EVIDENCE:
   - When official `livekit-client` (v2.23.0) publishes a track, it sends a `SignalRequest_Offer` with a sequential `id: uint32` (e.g. id=1).
   - In `internal/adapters/inbound/livekit/ws_handler.go` (lines 208-215), the synthesized publisher answer is returned as:
     ```go
     answerMsg := &livekitproto.SignalResponse{
         Message: &livekitproto.SignalResponse_Answer{
             Answer: &livekitproto.SessionDescription{
                 Type: "answer",
                 Sdp:  answerSDP,
             },
         },
     }
     ```
   - Notice that `Answer.Id` is not set (defaults to 0).
   - In `livekit-client`'s engine negotiation flow, the client snapshots `i = this.publisher.latestOfferId` (e.g. 1) and waits for the `"offerAnswered"` event with handler `s = e => { e > i && (o(), t()) }`.
   - Because `Answer.Id` is 0, `e` is 0, and `0 > 1` is false. The promise never resolves, and after 15 seconds the client throws:
     `[ClientA LOG] warning negotiation due to track publish failed, retrying after reconnect: NegotiationError: negotiation timed out`
   - Playwright test `02-bidirectional-rtp.spec.ts` times out at 30s as a direct consequence.

3. EXPECTED BOUNDARY BEHAVIOR:
   - For every inbound `SignalRequest_Offer` with `id := msg.Offer.GetId()`, the outbound `SignalResponse_Answer` MUST set `Answer.Id = id` (or `msg.Offer.GetId()`).
   - If available, `Answer.MidToTrackId` should also be populated to allow the client to map transceiver MIDs.

RFC / REQUIREMENT ID: REQ-003
SOURCE SERVICE: rtc-compatibility-suite
TARGET SERVICE: signaling-coordinator
STATUS: IMPLEMENTED
===================================================================

1. SUMMARY & TYPE:
   [Bug Fix | Inter-Service Protocol] Valid RTP capabilities in MediaStreamPort.Consume command

2. REASON & TECHNICAL EVIDENCE:
   - In `internal/application/room_actor.go` lines 287-295:
     ```go
     consRes, err := a.mediaStreamPort.Consume(ctx, &domain.ConsumeCommand{
         RequestID:             uuid.NewString(),
         RouterID:              a.room.RouterID,
         SubscriberTransportID: otherSession.Participant().SubscriberTransportID,
         ProducerID:            t.ID,
         RtpCapabilitiesJSON:   `{"codecs":[]}`,
         Paused:                false,
     })
     if err != nil {
         continue
     }
     ```
   - In `sfu-media-node` (Rust mediasoup), `can_consume(&producer_id, &rtp_capabilities)` validates whether the subscriber's RTP capabilities support the producer's codec.
   - When `codecs` is empty (`[]`), `can_consume` returns `false`, and `sfu-media-node` returns gRPC status `InvalidArgument / IncompatibleCodec: Router cannot consume producer with given RTP capabilities`.
   - The coordinator ignores this error with `continue`, resulting in no subscriber consumers being created, no media being forwarded through the SFU, and Bob never receiving Alice's RTP packets.

3. EXPECTED BOUNDARY BEHAVIOR:
   - `ConsumeCommand` sent to `sfu-media-node` must include the subscriber's actual or standard RTP capabilities (including opus audio and vp8/h264 video codec definitions with clock rates and payload types) so mediasoup router can establish the consumer.

RFC / REQUIREMENT ID: REQ-005
SOURCE SERVICE: rtc-compatibility-suite
TARGET SERVICE: signaling-coordinator
STATUS: IMPLEMENTED
===================================================================

1. SUMMARY & TYPE:
   [Bug Fix | Interop Blocker] Parse DTLS Fingerprints from all media descriptions (including m=application) and format DataChannel answer

2. REASON & TECHNICAL EVIDENCE:
   - When official `livekit-client` (v2.23.0) connects to `/rtc` and completes Join, it immediately initiates WebRTC PeerConnection negotiation before any audio/video tracks are published.
   - Chromium generates an initial publisher offer containing a WebRTC DataChannel:
     `m=application 9 UDP/DTLS/SCTP webrtc-datachannel`
     with media-level DTLS attributes:
     `a=setup:actpass`
     `a=fingerprint:sha-256 <hash>`
   - In `internal/adapters/inbound/livekit/sdp_mapper.go` (`ParsePublisherOffer`, lines 72-76):
     ```go
     for _, md := range s.MediaDescriptions {
         kind := domain.TrackKind(md.MediaName.Media)
         if kind != domain.TrackKindAudio && kind != domain.TrackKindVideo {
             continue
         }
         // Fingerprint extraction is placed AFTER this continue!
     ```
   - Because `md.MediaName.Media` is `"application"`, the loop triggers `continue` before extracting `a=fingerprint` and `a=setup`.
   - Consequently, `parsed.RemoteFingerprints` is empty (`len == 0`).
   - When `ws_handler.go` calls `coordinator.PublishTracks` -> `mediaNodeClient.ConnectTransport`, the Rust `sfu-media-node` rejects the transport connection with gRPC error:
     `livekit publish tracks error: failed to connect publisher transport: grpc connect transport failed: rpc error: code = InvalidArgument desc = At least one DTLS fingerprint is required`
   - Because of this error, `ws_handler.go` drops the offer and sends no SDP answer. `livekit-client` negotiation times out after 15 seconds with `ConnectionError: could not establish pc connection`, causing Gate 1 (`01-connection.spec.ts`) to fail.
   - Furthermore, in `GeneratePublisherAnswer` (lines 285-303):
     `ansMd.MediaName.Protos = []string{"UDP/TLS/RTP/SAVPF"}` and `ansMd.Attributes` appends `recvonly` and `rtcp-mux`. For `m=application`, this generates invalid SDP for data channels. `ansMd.MediaName.Protos` should preserve `md.MediaName.Protos`, and `recvonly`/`rtcp-mux` should only be added if `md.MediaName.Media != "application"`.

3. EXPECTED BOUNDARY BEHAVIOR:
   - In `ParsePublisherOffer`, extract `a=fingerprint` and `a=setup` from all `md.Attributes` regardless of media type (including `m=application`) before skipping non-audio/video media for track parsing.
   - In `GeneratePublisherAnswer`, for `m=application`, preserve `md.MediaName.Protos` (e.g. `UDP/DTLS/SCTP`), omit RTP attributes (`recvonly`, `rtcp-mux`), and preserve `sctp-port` if present.

RFC / REQUIREMENT ID: REQ-006
SOURCE SERVICE: rtc-compatibility-suite
TARGET SERVICE: signaling-coordinator
STATUS: IMPLEMENTED

1. SUMMARY & TYPE:
   [Protocol Compatibility | Route Handling] Support /rtc/ prefix in HTTP router for /rtc/v1 fallback elimination

2. REASON & TECHNICAL EVIDENCE:
   - Official `livekit-client` v12 protocol attempts connecting to `/rtc/v1?...` by default.
   - In `cmd/coordinator/main.go` line 131:
     `mux.Handle("/rtc", liveKitHandler)`
   - Go's `http.ServeMux` requires a trailing slash (`/rtc/`) to match subpaths such as `/rtc/v1`.
   - Currently, `/rtc/v1` returns HTTP 404, prompting client console errors:
     `WebSocket connection to 'ws://127.0.0.1:7880/rtc/v1?...' failed: Unexpected response code: 404`
     `warning Initial connection failed: v1 RTC path not found. Consider upgrading your LiveKit server version – Retrying`
     before falling back to `/rtc`.

3. EXPECTED BOUNDARY BEHAVIOR:
   - Register `mux.Handle("/rtc/", liveKitHandler)` alongside `mux.Handle("/rtc", liveKitHandler)` so that both `/rtc` and `/rtc/v1` route directly to `liveKitHandler` without 404 errors.

===================================================================
5. RESOLUTION & ARCHITECTURAL TRIAGE (REQ-005 & REQ-006):
   - Decision: ACCEPTED & IMPLEMENTED
   - Architectural Justification:
     1. [REQ-005]: Preserved Hexagonal SDP translation boundaries in inbound LiveKit adapter (`internal/adapters/inbound/livekit/sdp_mapper.go`). Moving DTLS setup/fingerprint parsing ahead of audio/video filtering ensures that DataChannel-only offers (e.g., initial Chromium offer without published tracks) correctly extract remote fingerprints to pass to the outbound `MediaStreamPort.ConnectTransport`. For answer generation, application m-lines retain their original transport protocols (e.g., `UDP/DTLS/SCTP`) and omit RTP-specific attributes (`recvonly`, `rtcp-mux`), while preserving SCTP port attributes.
     2. [REQ-006]: Registered `/rtc/` alongside `/rtc` in `cmd/coordinator/main.go` using Go standard library `http.ServeMux` subpath matching. This cleanly serves LiveKit protocol v12 `/rtc/v1` without breaking standard `/rtc` requests or introducing external routing dependencies.
   - Modified Files:
     - `internal/adapters/inbound/livekit/sdp_mapper.go`: Extracted DTLS attributes from all m-lines and formatted DataChannel answers cleanly.
     - `cmd/coordinator/main.go`: Added `mux.Handle("/rtc/", liveKitHandler)`.
   - Added Tests:
     - `TestSDPMapper_ApplicationDataChannelOffer` in `internal/adapters/inbound/livekit/sdp_mapper_test.go`
     - `TestLiveKitWSHandler_RtcV1Path` in `internal/adapters/inbound/livekit/ws_handler_test.go`
   - Verification: All 22 tests pass cleanly under `go test -v -race -count=1 ./...` with zero race conditions.
