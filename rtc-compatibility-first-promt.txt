# During Implementation — Mandatory Phased Execution

Follow the approved implementation plan strictly. Implement one slice at a time, verify its acceptance criteria, and do not proceed to the next slice until the current slice's gate is satisfied. Do not implement future phases prematurely.

### 1. Architectural Boundaries and Engineering Principles

Enforce the following five-layer Clean Test Architecture:

- `harness-app/`: Black-box browser application built with Vite and TypeScript, using the exact pinned version of the official `livekit-client`.
- `src/domain/`: Framework-independent domain models, gate states, evidence schemas, and test-result semantics.
- `src/controllers/`: Controllers and orchestration abstractions for token creation, participant lifecycle, browser interactions, and WebRTC statistics collection.
- `src/reporters/`: Evidence collection, report generation, status aggregation, and diagnostic output.
- `tests/`: Playwright gate specifications and reusable test fixtures.

Keep these layers logically separated and enforce dependency direction: domain logic must not depend on Playwright, browser APIs, infrastructure, or reporting implementations. Use dependency inversion where appropriate and inject external dependencies through explicit interfaces.

Apply SOLID principles, especially SRP, OCP, and DIP. Avoid unnecessary abstractions, speculative extensibility, duplicated logic, global mutable state, and business logic embedded in Playwright specifications.

Use the existing repository conventions where compatible with these requirements. If the repository's structure conflicts with the proposed architecture, document the conflict and propose the smallest justified change before proceeding.

### 2. Slice 1 — Harness Foundation, Controllers, and Evidence Infrastructure

Implement only the foundational harness and its supporting infrastructure.

Required deliverables:

1. `harness-app/`: A Vite + TypeScript browser application that imports the official, unmodified `livekit-client` package at the exact version pinned in the repository or explicitly approved during planning.
2. `src/domain/`: Typed gate status definitions, evidence-report models, and validation rules.
3. `src/controllers/`:
   - `TokenFactory`: Creates or obtains valid test credentials through an explicitly defined, configurable test-token mechanism. Never embed production credentials or secrets in browser code.
   - `ParticipantClientController`: Encapsulates browser participant interactions, publication/subscription operations, lifecycle management, and WebRTC `getStats()` extraction.
4. `src/reporters/`:
   - `EvidenceRecorder`: Collects execution evidence and generates `test-results/evidence-report.json`.
   - Report aggregation must preserve the exact status of every gate and distinguish test execution failures from infrastructure failures.
5. `docker-compose.yml`: Orchestrates `sfu-media-node`, `signaling-coordinator`, and any additional dependencies that are genuinely required for the integration tests. Reuse existing service definitions where possible instead of creating competing configurations.
6. Playwright configuration, reusable fixtures, deterministic test setup, and cleanup procedures.

The evidence report must record, at minimum:

- Exact pinned `livekit-client` version.
- Actual browser name and version used by the run.
- Execution timestamps and overall run status.
- Individual status and diagnostic information for every gate.
- Relevant signaling trace logs, with secrets and sensitive payloads redacted.
- Relevant RTP `getStats()` counters and observations.
- Explicit reasons for blocked, skipped, or not-run gates.

Use the following exact gate statuses:

- `PASSED`: The gate executed against the running services and all its acceptance criteria passed.
- `FAILED`: The gate executed and one or more acceptance criteria failed.
- `BLOCKED`: The gate could not execute because a required prerequisite or upstream gate failed.
- `NOT_RUN`: The gate was not attempted in the current execution, including gates not yet reached in a partial run.

Do not infer `PASSED` from successful compilation, mocked responses, static inspection, or service startup alone.

**Slice 1 acceptance criteria:**

- The application builds and TypeScript type-checking succeeds.
- The exact SDK version is verifiably pinned in the package manifest and lockfile.
- The services can be started using the documented Compose workflow, subject to required external configuration.
- The evidence-report schema and reporter are unit-tested.
- A controlled test run can generate a valid evidence report, including accurate statuses for gates that have not yet run.
- No real media connectivity or downstream gate is claimed to have passed at this stage.

Stop after Slice 1 and report the actual results. Proceed only when its acceptance criteria are satisfied.

### 3. Slice 2 — Gate 1: Connection and Gate 2: Bidirectional RTP

Implement and execute only Gates 1 and 2 after Slice 1 has been verified.

#### Gate 1 — `01-connection.spec.ts`

Acceptance criteria:

- An unmodified official `livekit-client` connects to the signaling coordinator through the intended `/rtc` endpoint.
- The client completes the expected connection and Join protocol exchange.
- The participant reaches the expected joined state.
- The evidence report contains the actual SDK version, relevant signaling events, execution outcome, and failure diagnostics.

Do not substitute a custom client, mocked protocol exchange, or modified SDK for the official client.

#### Gate 2 — `02-bidirectional-rtp.spec.ts`

Acceptance criteria:

- Two independent browser clients connect to the test room using the official, unmodified `livekit-client`.
- One client publishes audio and video, and the other successfully receives and renders them.
- Reverse-direction publication and reception are verified as well.
- WebRTC `getStats()` provides relevant evidence of actual media transfer, including positive `bytesSent` and `bytesReceived` deltas where applicable.
- Received video has non-zero rendered dimensions and demonstrable frame progression.
- Evidence distinguishes successful signaling from actual media-plane connectivity.

Use deterministic browser media fixtures or explicitly configured test media sources where practical. Do not interpret a non-zero cumulative counter from an unrelated connection or a previous run as proof of successful bidirectional RTP.

#### Sequential Gate Dependencies

Configure Playwright using an explicit sequential dependency strategy, such as a supported serial suite or a project dependency graph, with reliable failure propagation.

- Gate 2 must not run if Gate 1 has failed or has not been satisfied.
- Gates 3–5 must be recorded as `BLOCKED` when an unmet prerequisite prevents their execution.
- A gate must never be marked `PASSED` merely because it was skipped.
- Preserve independent diagnostic information about the root failure.
- Ensure that retries, worker restarts, test filtering, and partial runs cannot accidentally bypass prerequisites or produce misleading statuses.

Verify the behavior with a deliberate upstream failure and confirm that the resulting evidence report records the correct statuses.

**Slice 2 acceptance criteria:**

- TypeScript type-checking succeeds.
- Gates 1 and 2 execute against the running services.
- Their acceptance criteria are verified using actual browser and media evidence.
- The failure-propagation behavior is tested.
- Evidence is written to `test-results/evidence-report.json`.

Stop after Slice 2 and report the actual results. Do not implement Slice 3 until Slice 2 is verified.

### 4. Slice 3 — Gates 3, 4, and 5

Implement these gates only after the earlier slices have passed their required acceptance criteria.

#### Gate 3 — `03-concurrency-glare.spec.ts`

Verify concurrent publish/subscribe operations, overlapping negotiation attempts, and participant churn during active negotiation.

Acceptance criteria:

- Concurrent operations produce no unhandled protocol errors or unrecoverable state divergence.
- Participant, publication, and subscription states converge to the expected values.
- Any rejected or retried operation follows the protocol's defined behavior.
- The test uses deterministic coordination and bounded timeouts rather than arbitrary sleeps wherever practical.
- The report contains sufficient evidence to diagnose failures and distinguish expected contention from genuine state corruption.

#### Gate 4 — `04-simulcast-layers.spec.ts`

Implement and report two independent checks:

**A. SFU layer-selection capability**

- Publish a simulcast video track with verifiable spatial layers.
- Verify that the SFU supports the intended layer-selection operation.
- Verify the requested layer and the effective forwarding behavior using appropriate server-side evidence and receiver-side media statistics or frame observations.
- Distinguish an unsupported capability from a failed implementation or an inconclusive observation.

**B. Official LiveKit quality-update message mapping**

- Verify how the exact pinned official `livekit-client` represents and sends the relevant quality or subscription-setting update.
- Verify that the signaling coordinator correctly interprets and maps that message to the SFU's corresponding layer-selection operation.
- Confirm the resulting behavior, rather than merely asserting that a message was emitted.

Do not assume that LiveKit's protocol messages, quality settings, and mediasoup layer-selection APIs are semantically identical. Inspect the pinned SDK and actual protocol behavior before implementing the mapping.

Report the two checks separately so that partial success cannot be misrepresented as a fully passed Gate 4.

#### Gate 5 — `05-ice-restart.spec.ts`

Verify session and media recovery across an ICE restart.

Acceptance criteria:

- Trigger a real ICE restart through the supported client and signaling flow.
- Verify the expected signaling and ICE state transitions.
- Verify that media resumes or continues according to the intended recovery semantics.
- Use `getStats()`, connection state, and receiver-side observations to establish recovery.
- Distinguish successful signaling from successful media recovery.
- Include bounded timeouts, cleanup, and failure diagnostics.

Do not treat a successful `restartIce()` invocation or a return to `connected` as sufficient proof of media recovery.

**Slice 3 acceptance criteria:**

- TypeScript type-checking succeeds.
- Each gate executes against the running services and is evaluated against its own explicit acceptance criteria.
- Gate 4's two checks are separately represented in the evidence.
- All gate statuses accurately reflect actual execution.
- Failure propagation and the final evidence report are verified.
- All resources created by the tests are cleaned up reliably.

### 5. Mandatory Observability, Security, and Media Hot-Path Requirements

Apply observability requirements from the relevant repository skills across every slice. Observability must be designed into the harness and test infrastructure from Slice 1, not postponed until the final phase.

#### Configuration

Make applicable logging, tracing, sampling, and metrics behavior configurable through documented `OBS_*` environment variables.

Provide explicit configuration for:

- Log level and structured logging.
- Trace enablement, sampling, and propagation.
- W3C Trace Context (`traceparent`) propagation where applicable.
- Metrics enablement and endpoint configuration, including `/metrics` where supported by the service.
- QoE snapshot collection and its sampling or collection interval.
- Raw SDP logging, disabled by default.

Validate configuration at startup and document defaults. Do not claim that all observability is configurable unless the implemented behavior is actually controlled by these settings.

#### Cardinality and Media Hot Path

- Never use `room_id`, `peer_id`, `transport_id`, or `request_id` as Prometheus or VictoriaMetrics metric labels.
- Keep high-cardinality identifiers in structured logs and trace attributes only when justified and appropriately controlled.
- Never emit a log entry or create a trace span for every RTP packet or every unthrottled audio-level event.
- Use bounded-cardinality metrics, aggregation, sampling, and throttled snapshots.
- Avoid synchronous logging, expensive serialization, and blocking I/O on media-critical paths.

#### Security and Redaction

- Never log raw JWT `access_token`, ICE passwords (`ice_pwd`), credentials, private keys, or other secrets.
- Redact sensitive values from signaling traces, exception messages, test artifacts, and evidence reports.
- Raw SDP may be recorded only when `OBS_LOG_RAW_SDP=true` and the effective log level is `debug`, subject to the project's security policy.
- Keep credentials out of frontend bundles and client-visible configuration.
- Ensure test evidence is safe to retain and share.

Where the harness cannot directly observe a service's internal media-path behavior, document the boundary and use the service's supported telemetry rather than claiming unverified guarantees.

### 6. Verification and Reporting After Every Slice

At the end of each slice:

1. Run the applicable formatting, linting, and TypeScript type-checking commands, including `tsc --noEmit` where supported by the repository.
2. Run relevant unit and integration tests.
3. Execute applicable Playwright gates against the actual running services.
4. Verify evidence-report generation, gate statuses, and failure propagation.
5. Inspect logs and artifacts for leaked credentials, misleading statuses, and high-cardinality metric labels.
6. Record the exact commands executed, exit codes, and observed results.
7. List changed files, key design decisions, unresolved assumptions, known limitations, and the acceptance criteria that remain unmet.

If a prerequisite cannot be satisfied because of missing infrastructure, credentials, unsupported protocol behavior, or an environmental limitation, stop the dependent work, record the blocker, and request only the information necessary to proceed.

Never fabricate test results, service behavior, SDK compatibility, metrics, or completion status.

**Execution rule:** Complete and verify Slice 1 before Slice 2; complete and verify Slice 2 before Slice 3. Do not silently skip a failed acceptance criterion. Any deviation from this sequence requires an explicit explanation and approval.

Before reporting completion:
1. List changed files, explain how Clean Test Architecture and SOLID principles were applied, and document important design decisions.
2. Report exact commands executed and their actual results.
3. Separate passed, failed, blocked, and not-run tests based on actual execution.
4. List known limitations and unresolved assumptions.
5. Never claim a test passed unless it actually ran against the running services and passed.

- **Observability, Logging, APM & Metrics Requirement (Mandatory across all slices):**
  Read and strictly apply the project's observability skills (.agents/skills/*/SKILL.md).
  1. Make all logging, tracing (OpenTelemetry/W3C `traceparent`), and metrics (`/metrics` for VictoriaMetrics or QoE snapshots) 100% configurable via `OBS_*` environment variables so only configured levels and sampled events are recorded.
  2. Protect the media hot-path (never log or create spans per RTP packet or unthrottled audio level tick).
  3. Enforce strict metric cardinality guards (never put `room_id`, `peer_id`, `transport_id`, or `request_id` in Prometheus/VictoriaMetrics labels; keep them only in structured JSON logs and trace span attributes).
  4. Enforce security redaction (never log raw JWT `access_token`, `ice_pwd`, or secrets; only log raw SDP when `OBS_LOG_RAW_SDP=true` at `debug` level).
