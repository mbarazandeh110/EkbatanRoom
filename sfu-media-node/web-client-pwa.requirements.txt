RFC / REQUIREMENT ID: REQ-001
SOURCE SERVICE: web-client-pwa
TARGET SERVICE: sfu-media-node
STATUS: IMPLEMENTED

1. SUMMARY & TYPE:
   [Bug Fix | Network / WebRTC Security] Automatic Non-Loopback IP detection or documentation for MEDIASOUP_ANNOUNCED_IP

2. REASON & TECHNICAL EVIDENCE:
   - When `sfu-media-node` starts with default settings (or without `MEDIASOUP_ANNOUNCED_IP`), it announces `127.0.0.1` as the WebRTC ICE host candidate.
   - Per the W3C WebRTC specification and Chromium/WebKit WebRTC IP handling policy (RFC 8828), standard web browsers (Google Chrome, Edge, Safari, Firefox) running without `--allow-loopback-in-peer-connection` explicitly DISALLOW WebRTC PeerConnections to loopback addresses (`127.0.0.1` and `::1`).
   - When a user joins from a standard browser, Chromium silently ignores the `127.0.0.1` ICE candidate.
   - Consequently, no valid ICE candidate pairs are formed, the RTCPeerConnection remains in `connecting` state, and after 15 seconds `livekit-client` aborts with:
     `ConnectionError: could not establish pc connection`
   - When `sfu-media-node` is started with `MEDIASOUP_ANNOUNCED_IP=<non-loopback-ip>` (e.g., the LAN interface IP `192.168.x.x`), WebRTC connection succeeds immediately in under 60ms.

3. EXPECTED BOUNDARY BEHAVIOR:
   - When `MEDIASOUP_ANNOUNCED_IP` is not explicitly set, `sfu-media-node` SHOULD automatically detect the primary non-loopback network interface IP (e.g., `192.168.x.x` or `10.x.x.x`) instead of falling back to `127.0.0.1`.
   - Alternatively, documentation and default `.env` / `config.yaml` should explicitly mandate setting `MEDIASOUP_ANNOUNCED_IP` to the host's actual network IP for browser compatibility.

4. RESOLUTION & ARCHITECTURAL TRIAGE:
   - Decision: ACCEPTED & IMPLEMENTED
   - Architectural Justification:
     Automatic non-loopback IP detection via OS routing table probing (`detect_primary_non_loopback_ip`) has been implemented in `src/config.rs`.
     When `MEDIASOUP_ANNOUNCED_IP` is omitted, set to `"auto"`, or left `null` in `config.yaml`, `sfu-media-node` automatically detects the host's primary non-loopback IP (e.g. `10.x.x.x` or `192.168.x.x`) and uses it as the announced address in ICE candidates. This resolves the RFC 8828 loopback rejection in Chromium/WebKit browsers and eliminates the "could not establish pc connection" error.
     If all routing probes fail (e.g., in strictly isolated offline testing environments without a default route), it safely falls back to `127.0.0.1`.
     Setting `MEDIASOUP_ANNOUNCED_IP=none` explicitly disables announced_address, and setting an explicit IP overrides the auto-detection.
     `config.yaml` and `config.example.yaml` have been updated with `announced_ip: null` (auto-detect), and `README.md` documentation has been updated.
   - Modified Files:
     * `src/config.rs`
     * `config.yaml`
     * `config.example.yaml`
     * `README.md`
   - Added Unit Tests:
     * `config::tests::test_detect_primary_non_loopback_ip`
     * `config::tests::test_announced_ip_yaml_auto_and_none`

RFC / REQUIREMENT ID: REQ-002
SOURCE SERVICE: web-client-pwa
TARGET SERVICE: sfu-media-node
STATUS: REJECTED
===================================================================

1. SUMMARY & TYPE:
   [Bug Fix | RFC 3264 WebRTC SDP Compliance] Conform SDP Answer Direction for Inactive m-sections (`a=inactive`)

2. REASON & TECHNICAL EVIDENCE:
   - When a client participant unpublishes a media track (for example, stopping screen share), the browser WebRTC transceiver is set to `inactive`.
   - The browser generates an offer containing an inactive m-section per RFC 3264 Section 6.1:
     `m=video ...`
     `a=mid:3`
     `a=inactive`
   - Currently, `sfu-media-node` generates an SDP answer echoing `a=recvonly` (or `a=sendrecv`) for that m-section instead of `a=inactive`.
   - Per RFC 3264 Section 6.1: "If a stream is offered as inactive, the answer MUST be inactive."
   - In standard Chromium / WebKit WebRTC engines (`sdp_offer_answer.cc`), receiving `a=recvonly` in response to an `a=inactive` offer throws:
     `Failed to execute 'setRemoteDescription' on 'RTCPeerConnection': Failed to set remote answer sdp: Incompatible send direction`
   - This causes publisher renegotiation to fail with `unable to set answer`, negotiation timeout after 15 seconds, and websocket stream drops.
   - Note: `web-client-pwa` has implemented client-side defense-in-depth sanitization (`conformAnswerSdp`), but `sfu-media-node` should natively conform to RFC 3264 by setting `a=inactive` in the answer when the offer m-section is `inactive`.

3. EXPECTED BOUNDARY BEHAVIOR:
   - When generating an SDP answer, if the incoming offer's m-section has direction `a=inactive`, the answer's corresponding m-section MUST also be set to `a=inactive`.

4. RESOLUTION & ARCHITECTURAL TRIAGE:
   - Decision: REJECTED (Out of Domain Scope / Architectural Boundary Violation)
   - Architectural Justification:
     Per `.agents/rules.md` Section 1.1, Section 4.3.2, and `SIGNALING_CONTRACT.md`, `sfu-media-node` is a pure ORTC Media Plane built on `mediasoup-rust`. It communicates exclusively via gRPC (`proto/sfu/v1/media_engine.proto`) using ORTC structures (`RtpParameters`, `RtpCapabilities`, `DtlsParameters`).
     `sfu-media-node` has ZERO knowledge of SDP syntax, SDP offer/answer negotiation, transceiver media directions (`a=sendrecv`, `a=recvonly`, `a=sendonly`, `a=inactive`), or LiveKit protocol frames.
     All SDP offer/answer translation between browser clients and mediasoup ORTC objects is exclusively handled by `signaling-coordinator` (the Go service).
     Per our Cross-Service RFC protocol (`.agents/skills/cross-service-rfc/SKILL.md`), this requirement is REJECTED for `sfu-media-node` and has been forwarded as an outbound Cross-Service RFC to `signaling-coordinator` in `../signaling-coordinator/sfu-media-node.requirements.txt`.
   - Forwarded Location:
     * `../signaling-coordinator/sfu-media-node.requirements.txt` (REQ-001)
