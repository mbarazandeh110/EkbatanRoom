1. SUMMARY & TYPE:
   [Bug Fix | Bottleneck Report | Protocol & Media Pipeline Coordination]
   Resolve Video Consumer Layer Promotion Lock (`spatial_layer: -1` & `targetLayers: {-1, -1}`) under `livekit-cli` Load Testing: Coordinate initial video consumer preferred layer activation and keyframe synchronization between signaling and SFU pipeline to ensure RTP media egress to subscribers.

2. REASON & TECHNICAL EVIDENCE:
   - Verification of REQ-003:
     * Signaling coordinator implementation of REQ-003 was verified. `livekit-cli` receives `TrackPublishedResponse` with `mimeType: "video/vp8"` and valid `Codecs`.
     * Verbose execution logs confirm `livekit-cli` matches `p.MimeType()` against `SubscribedQualityUpdate`, eliminates the `subscriber requested backup codec but no track found` warning, sets `track.setDisabled(false)`, and logs `updating layer enable {"quality": "LOW/MEDIUM/HIGH", "enabled": true, "codec": "vp8"}`.
   - Comparative Differential Evidence (Audio vs. Video):
     * Audio Load Test (`./bin/lk load-test --audio-publishers 1 --subscribers 1 --duration 5s`):
       - 100% SUCCESS: 42 RTP packets received, 80.3 kbps bitrate, 0% packet loss, 1/1 tracks received immediately.
       - Proves UDP socket routing, STUN/ICE binding on `tun0` (10.8.0.4), DTLS handshake, and client-side Pion WebRTC `OnTrack` pipeline function properly end-to-end.
     * Video Load Test (Gate 1 Baseline Sanity: 1 publisher, 10 subscribers, VP8 Simulcast 720p/360p/180p, 30s):
       - 100% FAILURE: Connection Success Rate = 100.0% (all 11 WebSockets and PeerConnections connected), but ZERO media tracks received (`Tracks: 0/10`, `Bitrate: 0.0 kbps / NaNmbps`, 10 dropped tracks).
       - Single-layer VP8 (`--no-simulcast`) and H.264 also exhibit identical zero-track delivery.
   - Network Socket Layer Verification (`/proc/net/snmp` & `/proc/net/dev`):
     * UDP datagram counters during video test: Publisher transmitted ~130 KB (~150-210 UDP packets) to the SFU RTC port.
     * ZERO video RTP packets were forwarded by the SFU towards the subscriber sockets (egress bitrate = 0 kbps).
   - Server & C++ Engine (`mediasoup-sys` v0.23.0) Root Cause Attribution:
     Investigation of Mediasoup worker core (`SimulcastProducerStreamManager.cpp`, `Producer.cpp`, `Consumer.cpp`, `BitrateAllocator.cpp`) identified a dual-lock stalemate:
     1. Lock 1 - Initial Target Layers Suppression (`targetLayers = {-1, -1}`):
        In `SimulcastProducerStreamManager::ProcessRtpPacket`:
        ```cpp
        if (this->targetLayers.temporal == -1) {
            return DROP; // All incoming packets dropped with INVALID_TARGET_LAYER
        }
        ```
        When a consumer is created, `targetLayers` initializes to `{-1, -1}`. Layer recalculation (`RecalculateTargetLayers`) and BWE bitrate allocation (`BitrateAllocator`) only promote `targetLayers` if `producerRtpStream->GetScore() > 0` and `producerRtpStream->GetTemporalLayerBitrate() > 0`. At stream inception, bitrate evaluates to 0 bps. Crucially, `MayChangeLayers()` is ONLY invoked during lifecycle transitions and RTCP Sender Reports (`ProducerNewRtpStream`, `ProducerRtcpSenderReport`, `ProducerRtpStreamScore`, `OnResumed`) and NEVER on regular incoming RTP data packets. As a result, incoming RTP packets are dropped before BWE has an opportunity to allocate target layers.
     2. Lock 2 - Keyframe Promotion Guard (`currentSpatialLayer = -1`):
        In `SimulcastProducerStreamManager::ProcessRtpPacket`:
        ```cpp
        if (this->currentSpatialLayer != this->targetLayers.spatial && spatialLayer == this->targetLayers.spatial) {
            if (this->keyFrameSupported && !packet->IsKeyFrame()) {
                return BUFFER; // Discards/buffers until keyframe is received
            }
            shouldSwitchCurrentSpatialLayer = true;
        }
        ```
        Switching out of `currentSpatialLayer = -1` strictly requires an intra-frame (`packet->IsKeyFrame() == true`).
        When `Consume` is called on `sfu-media-node`, Mediasoup logs `Requested initial keyframe for video consumer` (`method:ConsumerRequestKeyFrame`), dispatching an RTCP PLI/FIR back to the publisher.
        However, `livekit-cli` is a synthetic test client that streams pre-recorded frames from an embedded IVF file (`ivfreader`) in a sequential loop. It does not possess an active video encoder to generate an IDR keyframe on-demand in response to in-band RTCP PLI/FIR.
        Because the initial IVF keyframe (frame 0) was already transmitted before the subscriber ICE/DTLS completed, Mediasoup's consumer never receives a keyframe on the target spatial layer. Consequently, `currentSpatialLayer` remains locked at `-1`, suppressing 100% of video RTP egress.
   - SLA Impact:
     Gate 1 (`gate-01-baseline`) failed with 10 dropped/missing tracks (Threshold: max 0). Violates Rule 1.2 ("No False Positives"). Downstream Gates 2-4 are BLOCKED per sequential gating protocol.

3. EXPECTED BOUNDARY BEHAVIOR:
   - Immediate Layer & Keyframe Synchronization:
     * When subscriber answers are finalized and consumer transports are established, ensure the SFU video consumer is activated with valid target layers:
       a) In `sfu-media-node`, configure the consumer's initial preferred layers upon creation or during `ConsumeRequest` (e.g. defaulting to spatial layer 0 or layer 2).
       b) Alternatively/additionally, `signaling-coordinator` should invoke `SetConsumerPreferredLayers` (gRPC `SetConsumerPreferredLayersRequest` to `sfu-media-node`) once the subscriber peer connection completes negotiation.
     * Ensure keyframe propagation is compatible with simulated / synthetic clients:
       a) Propagate signaling-level keyframe requests or negotiate keyframe cadence so publishers deliver a fresh keyframe after subscriber attachment.
       b) For synthetic test harnesses and video looper clients, ensure `sfu-media-node` / Mediasoup allows immediate stream promotion or handles initial packet tolerance so that the consumer transitions out of `spatial_layer: -1` and continuously forwards video RTP packets to subscribers.

4. RESOLUTION & ARCHITECTURAL TRIAGE (توسط سرویس مقصد پر می‌شود):
   - Decision: ACCEPTED & IMPLEMENTED
   - Architectural Justification:
     1. Strict Hexagonal Architecture & Clean Separation of Concerns:
        The resolution is implemented purely within the application layer (`src/application/media_service.rs`) and verified via domain entities, keeping transport and protocol boundaries clean without introducing external SDP/LiveKit dependencies into the core engine.
     2. Resolution of Dual-Lock Stalemate:
        * Lock 1 (Target Layers Promotion):
          During video consumer creation in `MediaService::consume`, default preferred layers are automatically resolved:
          - For Simulcast video streams (> 1 encodings), preferred spatial layer defaults to the highest available layer (e.g. spatial 2 for 3-layer 180p/360p/720p streams), with temporal layer 2.
          - For Single-layer video streams (1 encoding), preferred spatial layer defaults to 0, with temporal layer 2.
          - Configurable override via `MEDIASOUP_DEFAULT_VIDEO_PREFERRED_SPATIAL_LAYER` or `SFU_DEFAULT_VIDEO_PREFERRED_SPATIAL_LAYER`.
          - The resolved preferred layers are configured both during `ConsumerOptions` instantiation and explicitly invoked via `consumer.set_preferred_layers(pref).await` immediately upon creation, ensuring Mediasoup's C++ worker executes `RecalculateTargetLayers` and transitions `targetLayers` out of `{-1, -1}`.
          - `ConsumeResponse` now reports valid `initial_spatial_layer` and `initial_temporal_layer` values rather than -1.
        * Lock 2 (Keyframe Synchronization & Synthetic Client Tolerance):
          - Immediate PLI/FIR keyframe dispatch is executed upon video consumer creation and upon video consumer unpause/resume.
          - An asynchronous background retry worker was introduced (`tokio::spawn`), which periodically requests keyframes (every 500ms, up to 6 times / 3-second window) until `consumer.current_layers()` is promoted or the consumer/router closes. This ensures synthetic load generators (such as `livekit-cli` reading IVF files in loops) reliably align on an intra-frame even if the initial frame 0 was transmitted prior to subscriber DTLS completion.
          - Intra-node cross-worker pipe transports (`pipe_pair.pipe_consumer`) also trigger immediate keyframe requests when bridging video producers across workers.
        * gRPC `SetConsumerPreferredLayers`:
          - Verified and guaranteed to dynamically adjust preferred layers on demand and dispatch immediate keyframe requests.
   - Modified Files:
     * `src/application/media_service.rs`: Automatic preferred layers activation, fallback resolution, intra-node pipe keyframe propagation, and periodic background keyframe retry worker.
     * `tests/media_tests.rs`: Added comprehensive Simulcast integration tests (`test_video_simulcast_initial_preferred_layers_and_dynamic_update`), preferred layer logic unit tests (`test_resolve_default_video_preferred_spatial_layer_logic`), and assertions for single-layer consumers.
     * `rtc-load-suite.requirements.txt`: Updated status to `IMPLEMENTED` with complete architectural documentation.

RFC / REQUIREMENT ID: REQ-005
SOURCE SERVICE: rtc-load-suite
TARGET SERVICE: sfu-media-node (with signaling-coordinator coordination)
STATUS: ACCEPTED & IMPLEMENTED

1. SUMMARY & TYPE:
   [Bug Fix | Protocol & Contract Conformance | DTLS Transport & SDP Negotiation]
   Resolve Publisher DTLS Role Deadlock: Enforce Media-Level `a=setup` Attributes in Publisher SDP Answers and Assign Complementary DTLS Roles (Act as DTLS Client / Active Initiator via Mediasoup `role: client`) to Prevent Handshake Freeze and Restore RTP Media Transmission.

2. REASON & TECHNICAL EVIDENCE:
   - Empirical Packet Capture (`tcpdump` on UDP port range 40000-49999):
     * Capturing full UDP traffic during load testing (/tmp/audio-test.pcap & /tmp/video-test.pcap) revealed that on the publisher Mediasoup RTC port:
       - Exactly 16 packets were exchanged; EVERY SINGLE PACKET had byte 0 = 0x00 or 0x01 (STUN Binding Requests and Binding Responses).
       - ZERO DTLS packets were exchanged on the publisher transport.
       - ZERO RTP/SRTP packets were ever transmitted by the publisher or received by Mediasoup.
     * Clarification on Previous Audio Test:
       - In earlier audio runs, `livekit-cli` reported 42 packets (223.3 kbps). Packet inspection revealed payload type 127, SSRC 1234, payload string `"probator"`. These were Mediasoup Bandwidth Estimator dummy probe packets, not actual Opus media! The audio publisher was equally blocked by the DTLS deadlock.
   - Root Cause: Publisher DTLS Role Deadlock Mechanism:
     1. `livekit-cli` (Pion WebRTC) sends Publisher Offer with `a=setup:actpass` at media level (`m=application`, `m=video`, `m=audio`).
     2. `signaling-coordinator` sends Publisher Answer with `a=ice-lite`, and emits `a=setup:passive` ONLY at the global session level, omitting `a=setup` from media descriptions (`m=`).
     3. Mediasoup in `sfu-media-node`: `ConnectTransport` sets local role to `server` (`role: server`, state: 'before SSL initialization'). Mediasoup waits PASSIVELY for an incoming DTLS `ClientHello`.
     4. Pion WebRTC in `livekit-cli`: Because Mediasoup answered with `a=ice-lite`, Pion acts as ICE controlling. Because media sections omit `a=setup`, Pion's `DTLSRoleAuto` defaults an ICE controlling agent to DTLS `server` (passive)!
     5. DEADLOCK: BOTH SIDES ACT AS DTLS SERVERS. Neither peer transmits a DTLS `ClientHello`.
     6. Resulting Cascade:
        - The publisher PeerConnection remains permanently in `{"transport": "PUBLISHER", "state": "connecting"}`.
        - Pion blocks 100% of outgoing audio/video RTP packets over the unestablished DTLS transport.
        - Mediasoup never creates `srtpRecvSession` (`WebRtcTransport.cpp:1023`), and `IsConnected()` evaluates to `false`.
        - When `sfu-media-node` retries keyframe requests (`ConsumerRequestKeyFrame`), Mediasoup's `SendRtcpPacket` silently drops the RTCP PLI (`if (!IsConnected()) { return; }`).
        - The video consumer remains permanently suppressed at `spatial_layer: -1`.
   - Contrast with Working Subscriber Transport:
     * On the subscriber transport, `signaling-coordinator` synthesized the offer with `a=setup:actpass`, `livekit-cli` answered with `m=video ... a=setup:passive`, and `signaling-coordinator` configured Mediasoup as `role: client`. Mediasoup proactively sent DTLS `ClientHello`, and the handshake completed in <100ms.
   - Secondary Codec Alignment:
     * When `lk load-test` runs without an explicit `--video-codec` flag, `livekit-cli` offers `video/h264`, but `signaling-coordinator` sends `SubscribedQualityUpdate` with hardcoded `codec: "vp8"`, causing `livekit-cli` to leave publication `disabled = true`.
   - SLA Impact:
     * Gate 1 (`gate-01-baseline`) failed with 10 dropped tracks (0.0 kbps). Violates Rule 1.2 ("No False Positives"). Gates 2-4 blocked per Rule 2.2.

3. EXPECTED BOUNDARY BEHAVIOR:
   - In `signaling-coordinator`:
     1. Media-Level `a=setup` Enforcement:
        In `GeneratePublisherAnswer` (`internal/adapters/inbound/livekit/sdp_mapper.go`), append `a=setup:passive` (or `a=setup:active`) directly inside every active media description (`m=application`, `m=video`, `m=audio`).
     2. Active DTLS Role Assignment (Client Pattern):
        Ensure complementary DTLS roles are established: configure `a=setup:active` in the publisher answer and invoke `ConnectTransport` on `sfu-media-node` with `role: client` so Mediasoup initiates the DTLS `ClientHello` (mirroring the reliable subscriber transport pattern), OR force Pion to act as DTLS client by proper attribute placement.
     3. Dynamic Codec Alignment:
        Ensure `SubscribedQualityUpdate` dynamically reflects the published track's actual negotiated codec (`video/vp8` or `video/h264`) rather than hardcoding `vp8`.
   - In `sfu-media-node`:
     * Ensure `ConnectTransport` validates that publisher WebRtcTransports establish reciprocal DTLS roles and do not stay in passive initialization.

4. RESOLUTION & ARCHITECTURAL TRIAGE (توسط سرویس مقصد پر می‌شود):
   - Decision: ACCEPTED & IMPLEMENTED
   - Architectural Justification:
     1. Strict Hexagonal Architecture & Clean Separation of Concerns:
        The resolution is implemented cleanly across the inbound gRPC mapper boundary (`src/adapters/inbound_grpc/mapper.rs`), the transport application service (`src/application/transport_service.rs`), and the media application service (`src/application/media_service.rs`), with zero bleeding of SDP, Pion, or LiveKit protocol artifacts into the domain layer.
     2. RTP Header Extensions Support & BWE Congestion Control (Requirement 1):
        - In `mapper::parse_rtp_parameters`, support was added for both snake_case `header_extensions` and camelCase `headerExtensions` in incoming `rtp_parameters_json`.
        - Robust sanitization and normalization for header extension attributes:
          * `id`: numeric string and integer parsing, fallback lookup for `preferredId` / `preferred_id` / `extension_id`.
          * `encrypt`: boolean conversion, fallback lookup for `preferredEncrypt` / `preferred_encrypt`, defaulting safely to `false`.
          * URI normalization and whitelist validation: ensures `http://www.ietf.org/id/draft-holmer-rmcat-transport-wide-cc-extensions-01` (Transport-CC) and `urn:ietf:params:rtp-hdrext:sdes:rtp-stream-id` (RID for simulcast stream demuxing) along with `mid`, `abs-send-time`, etc. are preserved and passed to Mediasoup's C++ worker.
          * URL scheme normalization (`https://` -> `http://` for draft-holmer and webrtc experiments) prevents accidental filtering of valid extensions.
          * Sanitization of `encodings` array: integer `rid` (e.g. `0`, `1`) automatically converted to string to prevent serde deserialization failures.
        - In `MediaService::produce`, `ProducerOptions` receives the sanitized `RtpParameters` including the full header extensions list. This enables Mediasoup's C++ worker to receive Transport-CC feedback and compute Bandwidth Estimation (BWE) with the publisher, allowing the video stream to ramp up beyond the initial 180p@15fps baseline.
     3. Reciprocal DTLS Role Validation in ConnectTransport (Requirement 2):
        - In Mediasoup's ORTC model, `WebRtcTransportRemoteParameters::dtls_parameters.role` represents the *remote* endpoint's DTLS role.
        - When `ConnectTransport` is called with `dtls_role: "client"` (indicating Mediasoup should act as DTLS Client and actively initiate the handshake by sending `ClientHello`), `TransportService::connect_transport` assigns the complementary/reciprocal remote role `DtlsRole::Server` to Mediasoup. This instructs Mediasoup's C++ core to set `this->dtlsRole = CLIENT` and proactively send the DTLS `ClientHello`.
        - Conversely, when `dtls_role: "server"` is requested, Mediasoup is passed remote role `DtlsRole::Client` to act as passive responder.
        - For `dtls_role: "auto"`, Mediasoup receives `DtlsRole::Auto` and defaults to active initiator (`Client`), completely eliminating the dual-server freeze deadlock.
     4. Subscription Video Layer Activation & Promotion Guarantees (Requirement 3):
        - Verified and reinforced initial preferred layer resolution (`resolve_default_video_preferred_spatial_layer`): Simulcast streams default to highest spatial layer (Spatial 2, Temporal 2); single layer streams default to Spatial 0, Temporal 2.
        - Configured `options.preferred_layers` upon consumer creation AND immediately invoked `consumer.set_preferred_layers(pref).await` to unfreeze Mediasoup's C++ worker `targetLayers` from `{-1, -1}`.
        - Keyframe synchronization: Enhanced background keyframe retry worker in `tokio::spawn` with configurable retry count (`SFU_KEYFRAME_RETRY_COUNT`, default 10 attempts / 5-second window) and closed consumer guard (`consumer.closed()`), ensuring synthetic and real clients achieve intra-frame alignment and layer promotion to Spatial 2 / Temporal 2.
        - Immediate PLI/FIR keyframe dispatch on consumer resume (`set_media_paused`) and layer update (`set_consumer_preferred_layers`).
